Baseline Chapter 1

What performance means at this stage

Release blockers · target 0

  • Never state a fact the tools did not return.
  • Never answer about a product, order or customer the customer did not name.
  • Hold a conversation, and never carry data across sessions.
  • Create a return only when allowed, and never twice.
  • Never send an empty reply.

Core metric · higher is better

  • Give the customer what they asked for.
  • One pass or fail per question, reported as pass^k on the original questions and on held-out questions never used for tuning.

Tolerable for now, and not counted: missing details nobody asked for, imperfect wording, shortened product names.

Why pass^k is the headline number

The agent can answer the same question differently each time. A customer gets one answer, so it must be right every time.

  • pass^k ("pass all k"): run each question k times. It counts only if all k runs pass. pass^3 is the share of questions answered correctly in all 3 runs, so it measures reliability.
  • pass@k ("pass at least once"): it counts if at least one of the k runs passes. It shows what the agent can do, not what it does every time.
  • Example: a question that passes in 2 of 3 runs counts for pass@3 but not for pass^3. The gap between the two numbers is flakiness.

Iteration 1 Chapter 4

Better prompts, then better tools

Every change started from a failure in the error analysis, and was kept only if it helped.

The prompt: show the model which tool to call

The new prompt fixed four failure modes: B, C, D and F. Once it showed a plain email, the agent stopped inventing search syntax:

  • Long examples backfired: the model copied sample replies word for word or invented tool names.
  • Multi-step plans did not help: "search first, then look up" doubled the empty replies.
  • One fix can break another, so every change was checked on all question types.

The key finding: this model does not chain tools

"Is the Robot Vacuum in stock?" needs two calls: search_products finds the ID, then check_inventory uses it. Across five prompt versions the model did this in only 2 of 60 runs. LangGraph passes every tool result back, so the model has the information; it misses the planning step. So the tools changed to need only one call.

Chapter 6

Next steps

  1. Add planning and reflection to the agent

    An agent is made of five parts:

    • Model: the LLM that reads the request and writes the reply. It stayed qwen2.5:3b throughout.
    • Prompts: the instructions that tell the model how to behave. Changed in iteration 1.
    • Tools: the functions it calls to read and change store data. Changed in iterations 1 and 2.
    • Memory: what it keeps from earlier turns of the conversation. Added in iteration 1.
    • Planning and reflection: steps that decide what to do before acting and check the result before replying. Not added yet.

    The next iteration adds the last part: a planning step that chooses the tools before it calls them, and a reflection step that checks the reply against the tool results before it is sent. Most failures left happen after the agent already has the right data, so this targets them directly. Then rerun the same error analysis.

  2. Trace every agent run with MLflow or OpenTelemetry

    The biggest return for the effort. A trace records every model call and tool call in a request, with its timing, so it shows where the time goes from the customer's message to the reply. These latency numbers then decide how to add asynchronous processing and how to scale for staging and production.

  3. Score the brand voice with an LLM judge

    A judge with a written rubric scores each reply from 1 to 5 on five separate dimensions:

    • Brand personality: does the reply reflect the brand's personality?
    • Tone for the situation: is the tone right for what the customer is going through?
    • Wording: does it use the preferred wording and avoid jargon?
    • Conciseness: is it clear and direct, without filler?
    • Consistency: does it keep the same voice from start to finish?

    Check the judge against human ratings before trusting it, and add simple code checks for explicit brand violations.

  4. Split the agent into specialized agents

    LangGraph supports several agent nodes in one graph, so each area of support can have its own agent:

    • a recommendation agent that knows the products and their details;
    • a billing agent for orders and billing questions;
    • a post-purchase agent for returns, warranties and similar issues.

    Each agent sees only the tools and context it needs. Errors are easier to trace to one agent, each agent can be tested on its own, and each can use the model that fits its task, which saves cost.

Appendix

Glossary

What each failure code, label and metric on this page means, in plain English.

TermMeaning
Failure codes
A(invented_id)Invented ID. The agent called a tool with an ID that the customer never gave and no earlier tool returned, such as product 12345.
B(asked_customer_instead)Asked instead of looking up. The agent asked the customer for details it could have found itself with a tool.
C(empty_reply)Empty reply. The agent returned nothing, usually without calling any tool.
D(invented_search_syntax)Invented search syntax. The agent added made-up syntax to a search, such as email:bianca@example.com, so the search found nothing.
E(unknown_catalog_word)Word not in the catalog. The agent searched a word the catalog does not use, such as "skincare" for the Beauty category, and did not try again.
F(return_not_created)Return never created. The customer asked for a return, but the agent never called the return tool.
G(wrong_result_trusted)False answer from a wrong tool result. After an invented ID returned the wrong product, the agent answered as if it were the right one. It is a secondary code and always follows A.
H(invented_policy_fact)Invented policy or fact. The reply states a rule or a fact that no data supports, such as a 30-day return window.
I(stopped_mid_chain)Stopped mid-chain. The agent found the item but stopped before a second tool call it needed, such as the price after the stock check.
J(misread_tool_output)Misread the tool output. The reply contradicts the tool result in a way other than dates, such as calling an approved return "refunded".
K(tool_rejects_input)Tool rejects valid input. The tool itself failed, such as an email search that does not match capital letters.
L(order_date_mislabeled)Order date called a delivery date. The tool shows the order date only as "Date", and the reply calls it a ship or delivery date.
M(garbled_word)Garbled word. The reply contains a wrong word that changes the meaning, such as "subscribed" for "shipped".
Label fields
PassThe reply answers what was asked, every stated fact matches the database, and the agent did nothing harmful.
BorderlineA pass with a small gap, such as a missing extra detail or vague wording. It counts as a pass.
FailAny reply that is not a pass or a borderline pass.
First failureThe earliest step where a run went wrong. Each failing trace has exactly one, so the counts by code add up to the number of failures.
Secondary failureA later mistake in the same trace, written after the first code, as in A+G.
False claimThe final reply states something about orders, products, stock, returns or policy that the database contradicts or that no data supports.
Before / after the dataWhether the first failure kept the right data from reaching the model (A, B, C, D, E, K) or happened after the model had it (F, H, I, J, L, M).
How the item is namedHow the customer refers to what they ask about: a product name, a category, an email address or an order ID.
Metrics
pass^kThe share of questions answered correctly in all k runs. pass^3 means right every time in 3 runs, so it measures reliability.
pass@kThe share of questions answered correctly in at least one of k runs. It shows what the agent can do, not what it does every time.
pass^1The average pass rate of a single run.
Strict scorerA run passes only if every key fact of the reference answer is in the reply, every number came from a tool, and the reply is not empty.
Asked-for scorerThe same checks, but only for the facts the question asks for.
Hand-label pass rateThe share of the 141 traces of a stage that a reader labelled pass or borderline.
Scorer agreementHow often a scorer's pass or fail matches the hand label, measured on 40 audited runs.
Code checkAn automatic check that every number in the reply also appears in a tool result.
FlakyA question that passes in some runs and fails in others.
Evals and data
RunOne attempt by the agent at one question.
TraceThe full record of one run: every message, tool call and tool result.
Original questionsThe 35 questions that came with the assignment, run 3 times each.
Held-out scenarios43 scenarios written from the database and never used for tuning, run 2 times each.
Reworded questionsThe same questions in formal and casual wordings, to test that the agent does not depend on one phrasing.
Multi-turn sessions6 two-turn conversations, run 3 times each, to test that the agent remembers the first turn.
Edge cases S1–S1212 extra inputs written from the database before any run, such as an order that does not exist or a policy question.
Database truthThe correct answer, taken by a SQL query from a fresh copy of store.db.
